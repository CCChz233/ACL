# Harness 改进研究：Baseline 与对照协议

更新：2026-10-17。当前研究主线见 [研究故事](research_story.md)，执行顺序见 [下一步](next_steps.md)。本文定义研究对照。B0 已完成 [全部 Mini 50 题原始基线](mini50_baseline.md)：31/50（62%），无基础设施缺失，RSI=0。B4 的官方 RRSI 已完成单题完整流程，基准与新候选均通过、同分保留原版本；[全 50 题 B4 一轮](mini50_round1.md) 已完成，候选 29/50（58%），较基线退步并被拒绝；诊断耗尽后的有界恢复已披露。其他改进方法尚未运行，尚无改进净收益证据。

## 1. 比较维度与执行优先级

2026-10-18 更新：按官方研究来源和 Star 核查的 [首批外部框架清单](rsi_framework_selection.md) 已落地，GEPA、Meta-Harness、DGM、ADAS、Harness² 均已克隆锁版并开展离线检查。当前优先将 GEPA 接入相同提示编辑空间，再接 Meta-Harness；本次工程检查不等于这些方法已完成真实 Benchmark 或取得改进收益。下述 B0–B4 的方法定义保持不变。

区分改进模型 O、改进算法 A、公共运行框架 G、执行器 E 和初始目标 Harness H₀。比较模型时固定 A、G、E、H₀；比较算法时固定 O、E、H₀、任务与资源边界，尽可能共用 G，并披露无法统一的接口。

当前先以 B0 和 B4 跑通固定组合；校准后以固定 B4 比较改进模型，并补 B1、B2 隔离采样和结构化流程的作用。B3 用于后续检查算法依赖。再选择有代表性的模型配对做组件实验。Self-Harness 与 GEPA 按研究需要追加，不将所有方法、模型和组件做全组合。

## 2. 五个基础实验组

| ID | 名称 | 操作定义 | 主要问题 | 优先级 |
|---|---|---|---|---|
| B0 | Frozen Harness | 固定 H₀，在同一执行器及任务预算下评分 | 初始能力与改进增益是多少？ | P0 起必需 |
| B1 | Independent Best-of-K | 从相同 H₀ 和冻结的初始反馈独立生成候选；候选间不传递搜索结果；最后用允许的验证反馈选择 | 多候选采样是否已足够解释收益？ | B4 跑通并校准后加入 |
| B2 | Simple Iterative Improvement | 从当前版本与最新反馈提出修改，用固定规则决定保留或回滚；不向提议者提供全历史档案 | 简单反馈迭代能做到什么程度？ | 简化机制对照 |
| B3 | Meta-Harness-adapted | 允许改进者检索历史候选代码、分数与执行轨迹，并选择基于哪个候选提出修改 | 更丰富的历史利用能否改变差距与瓶颈？ | 后续外部方法 |
| B4 | RRSI-adapted | 固定官方 RRSI 的轨迹分析、受限提案、critic、成本正则化和脚本选择；接入相同 mini 目标与独立评分器 | 在较完整的固定 RSI 协议下，模型差异是否仍然存在？ | 当前工程底座和首轮主流程 |

### B4：当前固定的 RRSI 协议

使用 [google-research/rrsi](https://github.com/google-research/rrsi) 固定 commit，保持上游搜索和选择源码不变。模型调用边界适配 DeepSeek 原生工具协议，新增 mini-SWE-agent Domain；适配和预算必须对所有比较模型冻结。具体范围见 [运行说明](runtime.md)。本项目不是原论文任务/模型设置的数值复现。

analyst/digester、proposer、critic 与最终脚本接纳不是 D/P/I/V 的一一对应。critic 主要审核修改合理性和合法性，脚本依独立任务评分选择；不能把 critic 输出直接当作模型 verification 能力。后续组件替换需另定义接口，保留原生 B4 作参照。

### B0：基准与共享范围

每个 E、H₀、任务划分、执行配置组合测量一次规定重复数的基准；不同改进者可以共享这组测量。改进后候选仍需独立评分，并在不确定性估计中考虑共享基准，不能把同一个 B0 的复制记录当作额外独立样本。

B0 不消耗 Harness 搜索预算，因此不能把 B0 与搜索方法的成本宣称完全一致。分别报告搜索成本、部署成本，以及在明确后续部署任务量下的摊销成本。若要主张搜索优于把资源直接用于任务推理，另设增加执行预算的对照，不能由 B0 自动推出。

### B1：独立采样与选择

1. 初始证据来自同一 H₀ 的允许反馈，生成候选前冻结；所有组获得相同起始信息权限。
2. 每次从 H₀ 重置模型会话和可变状态，候选生成不读取其他候选及其分数。先完成候选生成，再揭示用于选择的验证结果。
3. K 和单候选生成、评测预算在校准后固定，服从总预算上限；无效候选也消耗已发生的生成与执行成本，不免费重采样。
4. 最终可选择 H₀。按预先指定的验证指标选择，分数相同时优先 H₀，其余平局用固定规则解决；不得用最终测试选最优候选。

这是无跨候选自适应的搜索控制，不是随机破坏代码。它仍可利用初始日志中的有效信息。

### B2：简单迭代与脚本选择

每轮向同一个改进模型提供当前代码及规定窗口内的最新反馈，生成并评测一个修改。反馈集可揭示允许的任务轨迹；验证集按约定揭示有限统计。接纳规则在校准后固定，例如验证分数提升至少阈值 ε 才替换当前版本，其余回滚。ε、重复评测次数、平局处理和最终提名规则在比较前冻结。

规则保证选择过程一致，不保证真实泛化收益。因随机评测而错误接纳的修改需要在独立评测中体现。每轮仍可对允许的证据做自主分析，不强制输出四阶段表单。

**B2 的接纳与回滚由脚本执行，所以 B2 本身不测量模型的 verification/selection 能力。** 验证能力需要第 4 节的专门实验；不能因为某模型在 B2 表现较差，就把原因归于它不会选择版本。

### B3：外部方法与适配记录

[Meta-Harness 论文](https://arxiv.org/abs/2603.28052) 允许提议者通过文件系统检索历代代码、分数和执行轨迹。[作者仓库](https://github.com/stanford-iris-lab/meta-harness) 提供框架与 Terminal-Bench 2.0 等参考实验，示例提议者使用 Claude Code。

在本项目使用公共运行框架、替换模型接口、统一 H₀、划分和资源限制后，名称为 Meta-Harness-adapted。保留全历史可检索这一关键机制，不简单将“普通循环加一句反思提示”冒充该方法。

接入时记录上游 commit、许可证、适配 diff、提议者框架、历史检索接口、候选选择、反馈披露和预算计量。首次验收先验证接口、记录与重置，不能把作者公开结果作为本地运行结果。

如果原生框架无法与 G 统一，可另列“原生系统”比较；其差异归属于整个系统，不能全部解释为算法本身或底层模型的效果。

## 3. 后续外部方法

| 方法 | 对照价值 | 接入条件与限制 |
|---|---|---|
| Self-Harness-adapted | 弱点挖掘、最小修改提案和回归验证的结构化流程 | 当机制研究涉及结构化支持时优先加入；统一编辑空间并披露与原协议差异 |
| GEPA | 反思式演化搜索，检查效果是否依赖特定搜索机制 | 明确使用 prompt 配置还是代码优化配置；不同编辑空间分开比较 |
| DGM 或 SICA | 经典 Agent 代码改进流程，检查结论是否跨改进算法 | 后续选择一个代表即可，控制额外工程和搜索开销 |
| Evo² | 已有改进者训练方法 | 进入参数训练扩展后重点比较；权重训练和搜索成本分别记账 |

[Self-Harness 原协议](https://arxiv.org/html/2606.09498v1) 使用回归评测结果决定修改接纳。即便其将该部分称为 held-out，在本项目中也应计为验证/选择数据，另外保留从未参与接纳或调参的最终测试。它原本强调同模型自改进；将改进者与执行器分开属于我们为角色隔离做的适配。

[GEPA 官方实现](https://github.com/gepa-ai/gepa) 的 optimize_anything 支持代码等文本产物，不应笼统描述为只能优化 prompt。若实现窄编辑空间版本，记录这种限制，并与相同编辑空间的其他方法比较。

HarnessOpt-Bench、HarnessDev 主要提供任务和评测设计参考；模型提供商的原生 Agent 和成熟人工 Harness 可作为系统参照，但不是自动改进算法。当前不将旧路线的 ReasoningBank 等经验检索方法列为首轮必需基线。

## 4. 组件与针对性支持的对照

组件分析采用独立于原生端到端方法的实验接口：诊断 D、计划 P、实现 I，以及按实验类型引入的验证/选择 V。先核对阶段化接口是否改变模型排序和收益，再在该接口内做替换。

| 组 | 做法 | 排除的解释 |
|---|---|---|
| C0 | 原生端到端流程 | 基础参照 |
| C1 | 同模型的 D/P/I 阶段化流程，沿用脚本选择 | 收益只来自分步骤或额外调用 |
| C2 | 在 C1 中逐一替换 D、P 或 I；其他阶段的模型、提示、预算固定 | 哪个阶段的替换改变后续收益 |
| C3 | 对有效组件做反向替换；必要时做两组件组合 | 单向帮助、交接兼容性或组件交互 |
| C4 | 冻结相同候选及相同可见反馈，比较模型选择、固定规则与随机有效候选选择 | 单独测量模型 selection，避免混入候选生成质量 |
| C5 | 给验证者相同起始状态及可补测预算，允许其设计评测并决定版本 | 测量主动验证与预算分配，并记录由补测增加的信息 |

C4 的随机选择仅是诊断参照，不是主要竞争方法。可在方法规则冻结后，用仅供离线分析的独立评分估计选错候选的损失；该分数不能回传给模型或用于正式候选提名。

C5 中模型负责实际的补测及选择，脚本只执行不可变的合法性和预算检查。如果脚本继续按分数替模型作接纳决定，就不能将其结果解释为模型验证能力。

替换 D/P/I 时，固定的是其他阶段的模型与配置，后续输出允许随上游内容改变。审计交接：D 不夹带完整补丁，P 不隐含额外私有评测，I 的修改应对应给定方案；无法满足时将其视为复合干预。加入同模型改写或相同信息的格式转换对照，检查效果是否仅来自更易使用的表达。

若发现瓶颈，再比较原始流程、通用支持、相同长度/调用资源的非针对性支持与针对性支持。强模型在线生成支持的成本完整计入，单独报告混合系统；教师输出不是 oracle，也不保证理论上界。

等长度只能控制长度，不能保证内容信息量相等。核心结论需结合交接审计、反向替换、预留设置复现和预算对照，而非仅凭一种消融成立。

## 5. 公平比较、开发与确认

- 所有方法共用 E、H₀、任务版本、容器资源、每任务执行上限和合法编辑范围；同一算法的跨模型比较使用同一 G。
- 固定资源上限，报告实际使用量，不为凑齐 token 强制无效计算。初始日志获取、候选评测、回归补测、选择调用和失败尝试都计入相关组成本；共享初始资产说明一次性与摊销口径。
- 以执行任务次数/重复次数和目标模型 token 计量评测；一个“评测调用”可以覆盖不同任务数，不能只比较调用次数。预算设硬上限，模型工具调用不能绕过计量。
- 接纳规则、候选窗口、K、阈值、停止条件及主要比较项在开发阶段选定。最终测试仅在候选提名之后运行。
- 方法开发场景内的独立审计结果可供研究者检查并修改方案，但一旦影响方法选择，该场景即属于开发数据，不能继续作为最终确认性证据。
- 根据开发结果选出的模型配对、组件和支持方式，在预留场景重新确认。探索性筛选与确认性实验分开；多个组件同时检验时预先指定主要对比，或处理多重比较。
- 记录搜索运行、初始快照和任务的层级。多条下游轨迹不能替代独立搜索；多个快照来自同一搜索时也不是完全独立样本。

不要求机制研究中的支持方法在所有任务上击败全部外部方法；需要证明瓶颈证据可靠、支持相对有效对照有价值，并明确适用范围。若只在简化 B2 上出现效果而在 B4 或 B3 消失，结论限定为该流程，不能包装成普遍瓶颈。

## 6. 最小实验顺序与成本

1. P0：完成 B0 与一次 B4 修改闭环，验收重置、日志、预算和评分。
2. P1a：固定 B4 下 3 个 Improver × 1 个 E × 1 个 H₀ × 至少 3 次独立搜索；共享 B0。用于判断能否测出差异，不能支撑通用排名。
3. P1b：固定有代表性的模型配对，补 B1、B2，按需要加入 B3，复用已有的 B4 比较。若差异只出现在某算法，记录算法依赖。
4. P2：先在共享快照上做局部 D/P/I 替换，验证能力另做 C4；选出有信号的组件再做反向替换及完整搜索确认。C5 按需要追加。
5. P3：针对性支持与匹配对照，在冻结规则后的预留场景复现；优先选一个迁移轴，再检查第二执行器。

20–30 个开发任务不代表实验便宜。例如，3 个改进者、3 次搜索、每次 8 个候选、每候选 20 个任务，已产生 1,440 次下游任务执行，尚未包含初始基准、重复验证及最终测试；这些数字仅为成本示例，不是冻结预算。代码与终端任务必须先测单次实际成本。

正式预算先由 P0/P1 的单次成本与方差估算，再确定候选数、任务数、搜索重复数及总费用上限。预算有限时优先减少模型/算法组合，保留关键对照和独立重复；不能用增加同一候选的任务轨迹数冒充更多改进运行。

## 7. 开跑前需冻结的配置

单题工程配置已记录模型、端点、G/H₀、编辑范围和预算；见 [运行配置](../configs/smoke.json)。正式比较仍需冻结独立 split 与来源审计、模型可追踪版本、K/ε/重复次数、预算、接纳/提名规则、主要统计对比及故障处理规则；不能直接照搬工程 smoke 的阈值 0。

先用开发资产完成这些选择，再保存带哈希的配置和数据清单。基础设施故障按预先定义的标准处理；模型造成的超时、无效修改与启动失败属于方法结果，不事后静默排除。Baseline 接入状态、上游版本和验收证据随实施更新。
