# Harness 自改进能力：受控测量、瓶颈识别与干预验证

更新：2026-10-17。本文是当前研究主线；研究结论均待实验检验。当前已完成 [全部 Mini 50 题原始基线](mini50_baseline.md)：31/50（62%），无基础设施缺失，本批 RSI=0。随后已完成 [全 50 题的一轮 RSI](mini50_round1.md)：候选 29/50（58%），较基线下降 4 个百分点，拒绝候选、保留原版。此前单题 RSI 同分。当前尚无改进净收益或模型间正式能力比较证据。运行状态见 [运行说明](runtime.md)。

首轮工程组合已固定：`google-research/rrsi` 为搜索代码、mini-SWE-agent 为被修改 Harness、DeepSeek 为改进模型及初始执行模型、SWE-bench 小规模开发子集为反馈任务。该组合先验收闭环，后续模型比较和对照仍需独立冻结协议。

本次修订补齐 [Baseline 与对照协议](harness_baselines.md)，并在第 13 节记录方案评估。当前方案可以进入工程预试验；正式比较还需冻结模型、数据划分、预算和选择规则。

## 1. 核心故事

现有自改进 Agent 已展示：在模型权重冻结时，修改提示、工具、上下文管理和执行逻辑等 Harness 组件，可以提高下游任务表现。但一个模型善于完成代码任务，并不自动说明它善于从执行证据中发现、实现和验证可泛化的系统改进。改进后的 Agent 表现还同时受到执行模型及其使用新 Harness 的能力影响，因此不能直接把端到端涨分解释为改进者的能力。

我们研究：**在受控的 Harness 改进过程中，哪些诊断、规划、实现和验证能力构成瓶颈？这些瓶颈在什么条件下出现，能否通过针对性干预被稳定补偿，并在未见任务和不同初始 Harness 上复现？**

研究先固定执行模型、初始 Harness、改进者运行框架、任务划分和预算，比较不同模型作为改进者的表现；再从相同状态出发，通过组件交叉替换识别差异来源；最后验证针对瓶颈的支持是否在相同总预算下提高后续 Harness 的质量。第一阶段不训练模型。只有在差距稳定、瓶颈明确、干预有效时，才考虑将相应能力定向蒸馏进 Qwen，并与一般代码训练及完整改进轨迹蒸馏比较。

当前证据链：

**受控测量 → 组件干预 → 瓶颈补偿 → 未见设置验证 → 有条件的参数训练。**

## 2. 当前决定与研究边界

- 当前不执行 SFT、LoRA、RL 或选择器训练；训练是条件扩展，不是论文完整性的前提。
- 主研究对象是有预算约束、基于反馈的 Harness improvement。首轮允许编辑目标 Harness，固定改进者自身的运行框架。
- 不预设强模型一定更善于改进，也不预设 Qwen 必然存在较大的改进能力缺口；先实测再选择机制实验的模型配对。
- 不预设 diagnosis、planning、implementation、verification 相互独立或覆盖所有能力。它们是便于干预的操作性划分，可能存在交互。
- “自己修改、自己执行”作为补充设置。若要进一步主张递归自改进，需要证明已有改进确实改善了后续改进过程，不能只报告任务成功率提高。
- 原外部记忆与经验组合方案保留为历史材料，不再作为首轮执行主线。

## 3. 与已有工作的关系

以下文献定位整理自 2026-10-15 的检索，供实验设计使用；不据此声称完整文献覆盖或首创，投稿前需更新检索并核对所用版本、协议和实现。

| 工作 | 与当前研究的关系 | 我们需要进一步回答的问题 |
|---|---|---|
| [SICA](https://arxiv.org/abs/2504.15228)、[Darwin Gödel Machine](https://arxiv.org/abs/2505.22954) | 已展示通过修改 Agent 代码提高任务表现 | 不再把“自动修改 Harness 有效”作为核心新意 |
| [HarnessOpt-Bench](https://arxiv.org/abs/2608.06301) | 直接比较模型的 Harness 优化能力，并使用隐藏测试；其改进者推理用量记录但不设上限 | 在明确的改进者和评测预算下，解释差异来源，而非仅增加排名 |
| [RRSI](https://arxiv.org/abs/2609.24972) | 正则化候选提案与选择，以降低演化过拟合并控制成本；当前工程底座及核心方法参照 | 区分模型能力与协议提供的支持，检验瓶颈在该协议下是否仍然存在 |
| [HarnessDev](https://arxiv.org/abs/2609.01437) | 比较 Harness 创建和演化，并区分创建模型与固定执行模型 | 从创建与演化的整体表现推进到可检验的组件瓶颈 |
| [Harness Updating Is Not Harness Benefit](https://arxiv.org/abs/2605.30621) | 区分更新能力和获益能力；在其编辑空间与协议下，小模型更新可接近强模型 | 差异在什么编辑空间和反馈条件下出现；不能预设弱模型不会改进 |
| [Priority Ranking / Shor](https://arxiv.org/abs/2605.22505) | 直接测量 Harness 组件修改优先级判断，并研究其与优化效果的关联 | 用实际后续执行检验诊断和规划干预的效果 |
| [Mendel Gödel Machine](https://arxiv.org/abs/2608.07645) | 讨论比较证据、诊断及编码专长与自改进表现的关系 | 通过组件替换检验机制，避免从模型间相关性推断能力独立 |
| [Learning Meta-Skills for Agent Harness Design](https://arxiv.org/abs/2609.38143) | 在冻结权重下学习 Harness 构建元技能，并检查跨 Builder、Target 迁移 | 确定具体瓶颈与干预条件，不把外部技能复用等同于参数内化 |
| [HMED](https://arxiv.org/abs/2610.07979) | 从恢复的相同发现状态比较元技能修改前后的后续搜索，并形成可复用记录 | 同起点比较已有先例；我们的重点是组件级定位与针对性补偿 |
| [Evo²](https://arxiv.org/abs/2610.13025) | 用 Harness 修改及执行结果训练 Proposer、Reflector，再进行后续搜索，执行模型固定 | 若加入训练，必须说明定向瓶颈训练相对既有改进者训练的额外价值 |
| [Harness-Zero](https://arxiv.org/abs/2609.24974) | 将优化 Harness 诱导的任务行为内化到模型 | 区分学会使用已有改进与学会发现新的改进 |

潜在贡献是对**差异的出现条件、组件瓶颈及其可干预性**形成可复核的证据。相关工作已经覆盖受控比较、元技能学习和改进者训练；把这些步骤串起来本身不足以构成新颖性。

## 4. 角色与实验对象

| 对象 | 定义 | 首轮约束 |
|---|---|---|
| Improver / 改进者 O | 根据目标 Harness 代码和允许的执行反馈提出、实现、评测并选择修改 | 仅替换模型；公共提示、工具和运行框架 G 固定 |
| Executor / 执行器 E | 在目标 Harness 中解决下游任务的模型 | 主比较中固定版本、推理配置和执行预算 |
| 目标 Harness H | 执行器的提示、工具包装、上下文管理及执行逻辑 | 从同一可运行 H₀ 开始，在公开声明的边界内允许修改 |
| 评测系统 | 管理任务重置、资源限制、数据权限、评分和版本记录 | 独立于可编辑目录；改进者不能改评分规则或查看封存测试 |

“固定 Harness”特指固定初始 H₀ 和改进者运行框架 G，不是禁止目标 Harness 演化。mini-swe-agent 可作为初始执行循环及公共改进者框架的候选；两种角色分别固定版本和配置，兼容性需先验收。

首轮编辑空间预先列清：执行提示、工具包装与观察格式、上下文整理、重试和停止逻辑等。模型端点、模型白名单、外部评分器、测试划分、资源上限及任务定义不可修改。目标 Harness 新增的模型调用也必须计入执行预算。

可用窄空间（仅提示或技能）和较广空间（允许执行代码修改）检查能力差异是否受编辑空间影响。该项为后续边界实验；首轮先选定一种，不同时展开所有因素。

## 5. 研究问题与可证伪假设

| 问题 | 待检验假设 | 不支持假设时如何处理 |
|---|---|---|
| RQ1：改进者之间是否有稳定差异？ | 固定 E、H₀、G 与预算后，不同 O 产出的 Harness 有可复现的测试增益差异 | 报告差异小或无法区分，检查编辑空间与反馈分辨率，不强行训练追分 |
| RQ2：差异能否由普通 coding 表现充分解释？ | 局部实现能力接近的模型，仍可能在证据解释、实验设计或版本选择上不同 | 承认当前证据未分离两者，不宣称独立的普适能力 |
| RQ3：哪些组件限制后续改进？ | 从同一状态替换特定组件，能稳定改变后续 Harness 质量 | 检查组件交互、交接接口或遗漏因素，不仅凭轨迹评分命名瓶颈 |
| RQ4：针对性支持是否有效？ | 基于诊断的支持，优于相同资源下的通用支持，并可在未见设置复现 | 将效果限定为当前条件；无法复现时不声称可迁移补偿 |
| RQ5：是否值得训练？可选 | 已识别瓶颈的定向训练，比一般代码训练或完整轨迹蒸馏更有效 | 若无额外价值，保留不训练的机制研究主线 |

RQ2 不靠少数模型的榜单相关性单独回答。应同时测量相同方案下的实现能力，并检查组件替换是否改变改进表现。结论限定为“在当前协议下不能由所测 coding 表现充分解释”，而非两种能力完全独立。

## 6. 测量协议与数据边界

主指标为给定执行器上的测试增益：

\[
\Delta(O;E,H_0,B)=S_{test}(E,H^*_O)-S_{test}(E,H_0),
\]

其中 H* 由改进者仅利用允许的开发与选择反馈，在预算 B 内选出；测试分数不参与选择。比较模型时固定 E 和 H₀，并重复独立搜索。

数据分为三个层次：

1. **工程检查与校准资产**：用于适配、空补丁/参考解、重置及预算校准；不计入最终未见证据。
2. **方法开发场景**：每个场景有反馈集、选择集和独立审计任务。反馈集可提供允许的任务信息、结果与轨迹；选择集只提供预先约定的有限反馈；独立审计任务不参与模型搜索。研究者若利用审计结果调整方法，该场景仍属于开发数据，不能称为最终封存测试。
3. **最终未见场景**：冻结干预规则及所有超参数后，换用预留的任务组或初始 Harness，再从头改进并最终评分。用于检验机制和支持能否迁移，而不只是最终 Harness 能否解同分布新题。

代码按仓库及任务血缘审计，终端按来源、模板和内容审计。若初期只能做同仓库任务拆分，要明确这是同仓库泛化；不能称为跨仓库泛化。用于方法选择的场景不能继续当作未见场景。

改进者可以看到反馈任务的失败证据，但不能看到封存任务的参考补丁、隐藏测试、答案或评分。执行器仅能访问下游协议允许的仓库测试及工具。历史经验、缓存和搜索树在独立运行间重置；保存证据时区分私有评测材料与可发布日志。

同时报告以下结果：

- 初始与最终成功率、绝对增益，以及相对同一 H₀ 的配对差值；不同领域分别报告。
- 随预算变化的独立评分曲线、达到给定收益的成本、回归率及最终候选选择失误。检查点预先固定，隐藏曲线不反馈搜索。
- 改进者 token/模型调用、目标评测任务次数与 token、最终执行成本、时间及基础设施故障。
- 两类重复：独立改进运行与下游任务重复执行。统计时保留搜索运行和任务/仓库的层级结构，不能把同一 Harness 的大量任务执行当作独立改进实验。

预算 B 分开约束改进者推理、目标评测和每任务执行；使用成本曲线补充单点比较。相同轮数或调用数不等于相同预算；不同模型的 token、价格和延迟也不等价。校准后预先写明主要预算口径、数值和停止规则，并保留其他用量，不能根据正式结果逐模型调整。

### Baseline 的职责

基础组为 B0（不修改 H₀）、B1（独立候选采样与验证选择）、B2（简单反馈迭代、脚本接纳）、B3（Meta-Harness-adapted，全历史可检索）和 B4（固定官方 RRSI 的分析、提案、critic 与正则化选择）。先以 B0/B4 跑通工程、校准并比较模型，再在代表性配对上加入 B1/B2，按需加入 B3，不从一开始做所有组合。Self-Harness 与 GEPA 按机制问题追加。具体操作、适配限制和计费口径见 [Baseline 协议](harness_baselines.md)。

B0 测基准能力，B1 控制多次尝试，B2 测简单反馈循环，B3 检查更丰富的历史利用，B4 测完整固定协议下的改进表现。固定同一算法比较模型；固定模型比较算法。对照方法的接入和预算修改需要披露，不把原论文分数直接用于当前实验横向比较。

## 7. 组件干预：从相关性走向机制检验

先保存可恢复快照：当前 Harness、允许的执行日志、候选历史、已用预算和当前阶段。建立统一的阶段输入输出接口，再进行交叉替换。

| 组件 | 输出内容 | 干预方式 | 主要观察 |
|---|---|---|---|
| Diagnosis | 有证据支持的失败机制、竞争解释与不确定性 | 固定其余阶段，替换诊断 | 后续修改是否解决可复现机制，并改善未见任务表现 |
| Planning | 候选干预、预期效果、区分假设的实验及预算安排 | 给定相同诊断，替换计划 | 是否用有限评测区分方案，而非无方向搜索 |
| Implementation | 把明确方案转为可运行修改 | 给定相同诊断和方案，更换实现模型 | 启动、工具兼容、实现忠实度及下游收益 |
| Verification / Selection | 解释验证反馈，决定补测、保留、回滚或停止 | 给定相同候选与反馈，替换选择阶段 | 是否识别噪声、避免回归，并选出更好的最终候选 |

冻结候选池的选择实验只测决策能力；允许主动补测的实验同时涉及实验设计与预算分配，两者分开报告。

先比较全弱、全强以及 D/P/I 的单组件替换，再对有效组件做反向替换及必要的组合实验。“强/弱”由开发阶段的重复结果确定，不以模型品牌预先指定；筛选后的配对和主要干预在预留场景独立确认。

**验证能力单独定义实验。** B2 与当前 B4 的最终接纳由脚本执行，所以它们的结果不直接测量模型最终选择能力；B4 的 critic 不能替代该实验。先冻结候选池与可见反馈，比较不同模型选择、固定规则和随机有效候选选择；需要研究主动验证时，再给验证者相同起点及补测预算，让模型实际决定补测和版本选择。合法性与资源限制仍由不可变脚本执行。

所有分支从相同快照开始；控制输入信息、输出格式、交接长度和可用预算。强模型提供的内容不能夹带弱组未获允许的额外评测或答案。分别记录局部干预的上游生成成本，以及端到端相同总预算下的净收益。

阶段化会改变原生搜索行为，因此保留不强制分阶段的端到端基线。局部替换的效果只解释该接口下的干预，不直接等同于模型内部能力的完整分解。

组件效果还可能来自更完整的信息、较易使用的交接表达或跨模型兼容性。核查诊断是否夹带完整方案、计划是否夹带补丁或额外评测；加入同模型阶段化、同信息格式转换及预算匹配对照。无法隔离的输出应报告为复合干预，而非纯诊断或纯规划能力。

轨迹标注和模型评分用于辅助诊断；关键结论依赖真实后续执行。抽样人工盲审证据与实现一致性，不以某个教师对自身输出的评分代替验证。

## 8. 不训练的瓶颈补偿与迁移验证

若某组件被重复干预支持，再设计针对性支持，例如诊断证据模板、竞争假设检查表、实验设计指导，或验证与回滚规则。支持的具体形式由开发结果决定，不提前认定诊断必然是瓶颈。

至少比较：原始流程、通用支持、相同长度/资源的非针对性支持、针对已识别瓶颈的支持。所有额外模型调用和验证均计入预算；若每次由强模型在线供给组件，应将其报告为混合系统及其成本。

冻结支持规则后，在预留任务组及不同 H₀ 上重跑；再用第二个执行器检查结论对模型配对的依赖。首轮只选择一个主要迁移轴，避免同时扩张模型、领域和 Harness。

支持有效说明系统瓶颈可补偿；外部技能或提示的跨模型复用说明上下文层面的迁移。二者都不能单独证明能力已进入学生权重。

## 9. 可选训练：何时启动、如何证明价值

只有同时满足以下条件，才进入训练设计：

1. 固定执行器后的改进者差异超过重复运行噪声，并在预留设置中得到支持。
2. 组件替换和反向检查支持一个可操作的瓶颈，而非只有相关性。
3. 针对性支持在记录完整成本后仍有效，且能够形成可检验的训练监督。

届时比较原始 Qwen、一般代码修改训练、完整 Harness 改进轨迹蒸馏、瓶颈组件定向蒸馏，以及教师参照。学生训练组尽量匹配训练 token、优化计算和数据获取资源；无法同时匹配时分别记账。

主训练评测只改变 Improver，Executor 保持同一个冻结模型；每次清空已有 Harness 改进，从 H₀ 或未见 H₀ 重新搜索。训练任务、Harness、轨迹及其近重复与最终场景分开。训练数据包括失败、无收益和拒绝修改的证据，而非仅模仿成功补丁。

主要检验学生是否更善于产生新的改进，以及收益是否对应目标组件；同时测普通 coding 表现。不要求 coding 完全不涨，但需要训练对照来排除一般代码训练就足以解释结果的情况。学生自己执行的设置另列，避免把执行能力增强误算为改进能力增强。

## 10. 执行阶段与继续条件

| 阶段 | 工作与交付物 | 继续条件 |
|---|---|---|
| P0 工程验收 | B0 与一次 B4（RRSI）修改闭环；1–3 个工程检查任务；保存重置、评分、预算和完整日志 | 评分与环境可信，修改不能绕过预算或封存边界 |
| P1a 校准与比较 | 约 20–30 个开发任务校准；固定 B4 下 3 个 Improver × 1 个 Executor × 1 个 H₀ × 至少 3 次独立改进，共享 B0 | 反馈有分辨率；该规模只用于先导判断，不是论文充分样本量 |
| P1b 算法参照 | 对代表性模型配对补 B1/B2，按需加入 B3，检查模型差异是否依赖 RRSI 流程 | 明确采样、迭代和历史利用的影响；避免把单流程现象过度推广 |
| P2 组件定位 | 共享快照上做 D/P/I 替换；验证选择另做实验，再补反向替换与完整搜索确认 | 找到可复现的局部效果，或得到明确的否定证据 |
| P3 干预与泛化 | 冻结针对性支持，与通用/资源对照比较，在预留场景复现 | 确定有效及失效条件，检验能否形成可复核的机制证据 |
| P4 可选训练 | 定向蒸馏及训练对照；新 Harness 上重新搜索 | P1–P3 满足条件，且训练有明确待回答问题 |

正式规模由 P1 的搜索运行方差、任务方差、预期效果与资源测算确定，在封存评测前冻结。若模型差异很小，先检查编辑空间、反馈质量及执行器获益能力；若干预无效，保留否定结果并缩小结论，不靠堆训练掩盖问题。

若不训练阶段的最终结果已用于决定后续训练设计，这些场景应转列开发记录；训练扩展需要新的独立确认数据，不能继续使用同一批结果宣称未见泛化。

## 12. 日志与论文交付

每次改进运行至少记录：run/scene ID，所有模型版本与配置，G 和 H₀ 哈希，split 版本，种子，预算上限与实际用量，候选/父版本/修改 diff，阶段输入输出及证据引用，评测记录，接纳/回滚/停止理由，最终候选 ID，基础设施故障和独立评分记录。测试记录单独存储，不供改进者读取。

预期论文交付包括：受控改进者比较、组件替换结果、针对性支持的成本与泛化结果、正反案例及可复现版本记录。训练结果若实施则单列；不能提前写入论文结论。

| 证据 | 允许支持的结论 | 不能直接推出的结论 |
|---|---|---|
| 固定 E 的重复改进差异 | 该协议和编辑空间下改进表现不同 | 通用的模型自改进能力排名 |
| 组件替换改变后续收益 | 该接口下组件干预有效 | 模型内部存在完全独立的同名能力 |
| 针对性支持在未见设置有效 | 系统瓶颈可被补偿，效果有明确适用范围 | 学生权重已获得该能力 |
| 定向训练优于资源匹配对照 | 目标能力可在所测范围内学习并改善后续改进 | 已实现普适 RSI 或递归加速 |

## 13. 方案评估与最小证据链

**总体判断：研究问题与证据链合理，可以开始 P0/P1 的工程和现象预试验；新颖性尚未由结果确立，当前配置也未达到正式实验冻结条件。** 不训练可以完成机制研究，但仅有模型排行榜、轨迹分类或一组教师帮助涨分不足以支撑当前故事。

| 方面 | 当前判断 | 必须补足的证据或设计 |
|---|---|---|
| 研究价值 | 能检验自改进表现的具体瓶颈，且允许否定结果 | 提供局部干预与后续执行的联系，界定有效范围 |
| 与已有工作的区别 | 受控比较、元技能和改进者训练都有直接先例 | 找到组件机制或出现条件的实质发现；不能只靠组合现有步骤 |
| 可解释性 | 固定 E 与 H₀ 是必要起点，但单一执行器不能完全消除 Harness–模型交互 | 第二执行器检查；分开脚本选择与模型验证，控制交接与信息差异 |
| 泛化 | 预留任务与初始 Harness 的设计方向合理 | 开发场景筛选的发现必须在独立场景确认，不能重复使用“封存”标签 |
| 可执行性 | 当前数据和源码可复用，但运行闭环尚未完成 | 明确模型配置、预算、划分、编辑接口、提名与故障规则 |
| 成本 | 方法、模型、任务、候选和重复数会相乘 | 首轮先 B0/B4，后补 B1/B2，按需加入 B3；组件筛选先局部续跑，再确认完整搜索 |

最小可交付证据链为：在明确协议下测到可复现现象；至少一个组件干预在交接、信息与资源对照后仍有可解释效果；针对性支持在冻结规则后的预留场景有收益或明确失效边界；保留竞争解释与否定结果。不要求支持方法处处击败所有外部方法，但若效果只存在于 B2，应将结论限定在该流程。

工程配置已固定 DeepSeek 端点、G/H₀ 和 smoke 预算；正式比较前仍需冻结模型版本、独立数据清单、校准预算、候选/接纳/停止规则、主要对比和重复规模。当前可执行的下一步是先完成一次可信闭环，再根据实测成本与方差确定这些数值。

下一步以 [执行清单](next_steps.md) 为准，组别操作以 [Baseline 协议](harness_baselines.md) 为准。历史方案见 [外部经验 Baseline](baseline_protocol.md) 与 [早期研究方案](research_plan.md)。
