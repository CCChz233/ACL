# 当前高预算重跑：两轮、必须交付实际 Harness 修改

2026-10-19。用户认为“未更新/沿用H0”不足以回答框架比较，明确要求加大步骤重跑，必须产出修改。本实验从共同H0重新启动五框架各两轮；原低预算两轮结果和全部失败记录保留，不能覆盖或把旧分数当作新一轮结果。

当前入口 `acl_multiround_v3`，配置 `configs/full10-highbudget-two-rounds-v1.json`，工作区 `experiments/runs/full10-highbudget-two-rounds-v1/`，tmux `acl-full10-highbudget`。以 `batch-status.json`、各轮 `result.json` 及官方逐题评分为准；后台启动不代表已经交付或评完。

## 固定部分与提高预算

模型仍固定 DeepSeek Flash、thinking=false、同一端点；Agent、困难十题、共同H0 3/10、修改范围、Docker镜像、官方grader都不变。每题仍50次调用／100万token／4096输出token／1200秒，命令60秒，评分900秒。全部50个任务镜像永久保留，串行运行。

每框架每轮优化由80次／100万token提高到 **400次／800万token**，输出仍4096。原生阶段先限300次／600万token，为原生续写和模型门禁修复保留余量；所有角色、续写和修复共享同一请求与usage账本，累计不超过400次／800万token。搜索墙钟7200秒，框架进程保护36000秒。

五框架各两轮，最多10个最终评测候选、100次新任务执行、9000次新请求和1.8亿实际/保守预留token。这里是新重跑的上限，过去低预算消耗单独留档，不从历史账本删掉。没有外部基础设施的隐式付费重试。

## 必须交付的定义

必须相对本轮父代有真实代码或提示内容变化；只复制父代、只改注释或提示空白不算。统一检查Python、全部四个Jinja模板、固定YAML范围、许可证、构造、单/多工具及提交时的工具结果配对。模型不得写入任务专用答案、仓库专用规则、额外依赖、宿主/凭证或评分访问。

没有生成有效修改时标为 `delivery_failed`，不允许把H0缓存成绩写成成功交付。下一轮只能从有完整十题轨迹的本框架原生保留版本继续；若交付或基础设施中止，缺失分数保持缺失，不填零。

**有效修改不等于通过率提升。** 即使真实候选比原始Agent差，也记录实际成绩及原生接纳决定，不通过挑选有利分数来“证明有效”。

## 原生阶段和交付保障

- HarnessFix仍执行原生分析、聚合计划、实现、plan/diff audit与promotion。单题分析上限仍20步，规划从20提高到60步，实现从40提高到100步；原生plan/diff audit不被绕过。实现后先过统一门禁；原生audit失败时可由模型按同一原生计划修正后再审查。
- Meta-Harness仍使用原生frontier和文件提案器。候选目录预先复制父代（这不是修改），要求模型用小范围Edit完成真实机制，然后Finish；避免花预算重写未改变的整个源文件和许可证。统一门禁拒绝原样提交。
- RRSI仍使用Analyze/Propose/Critic/Evaluate/Select。分析师3轮、digester6轮，避免诊断阶段吞掉全部预算；proposer由40提高到80轮，必要时由同一原生proposer继续完成。有效性修复放在原生critic和git提交**之前**，critic看到实际修复后的diff。
- GEPA仍原生反思edit-spec搜索；材料化产物过统一门禁后才评测。
- DGM仍原生父代mini自修改与archive流程，并保留已声明的空列表兜底。原生候选在进入archive/评测前过统一门禁。

每轮最多两次原生检查点执行，所有请求仍受同一400/800万账本约束。原生续写、角色上限调整和模型有效性修复全部单独标记，因此这是**高预算、带交付保障的工程比较**，不是只改变预算的严格消融，也不是未改原论文配置的复现。

## 模型修复与审计

仅修复框架自身生成的候选产物或原生计划下的实现。门禁错误由同一DeepSeek在限定的公开文件工作区处理，操作者不手写候选代码。每轮最多3次修复会话，均计入400次／800万token，不增加任务评测次数。

`delivery/repair-N/{before,after,record.json}`保存原生候选前后源码、摘要、失败原因、采用的原生计划/诊断文件与“未使用当前候选测试反馈”的声明。模型文件读写及请求/usage均留档。一旦任何真实任务执行开始，禁止再修复或更换该候选，防止看过分数之后改代码。

34项离线检查已通过，详见 `offline-validation.json`。付费开始前冻结当前源码、配置及完整源码副本，旧冻结依赖链继续核验，不修改历史源码。
