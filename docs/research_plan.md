# 代码与终端 Agent 的 RSI 定位与 Benchmark 方案

核对日期：2026-10-12。本文确定研究范围和建议评测方案；尚未完成数据去重、环境复现或模型试跑。

## 研究定位

面向代码与终端 Agent 的可靠持续自改进：Agent 从代码修改、测试、构建和终端操作中积累经验，研究这些经验如何在新的任务、仓库、环境和模型能力阶段中继续产生收益。

代码是任务领域，终端是执行界面。仓库级软件工程和一般终端工作流是两个相互关联、但应分别报告的任务分布。不能因为 SWE Agent 使用 shell，就把 SWE 测试结果等同于终端工作流泛化。

当前研究假设：同一条经验在外部检索和参数内化中的效用可能不同；根据经验适用条件和 Solver 当前状态决定检索、内化、暂存或删除，可能比固定使用规则更可靠。这是待验证假设，尚不能声称新颖性已成立。

原 Solver + Trainer 主线保留：如果经验使用机制能够随反馈改进，冻结初始与最终机制，重置 Solver、适配器、优化器和运行记忆，在独立任务及相同预算下比较其训练效率。需要额外比较强固定策略和等预算独立搜索，不能只比较初始与最终版本。

## 建议评测组合

| 角色 | 数据集 | 需要回答的问题 |
| --- | --- | --- |
| 代码主测试 | SWE-bench Pro V2，公开 642 任务 | 新的真实仓库任务上是否更能修复问题 |
| 终端主测试 | Terminal-Bench 4.0.0，固定版本快照 | 更广泛的终端工作流上是否有效 |
| 终端参考测试 | Terminal-Bench 2.1，89 任务 | 与既有研究在同一版本、预算和 Agent 条件下对齐 |
| 代码参考测试 | SWE-bench Verified，500 任务 | 与历史 SWE Agent 工作对齐，作为补充证据 |
| 可选语言迁移 | SWE-bench Multilingual，300 任务 | 若主张跨语言迁移，再追加独立验证 |

SWE-bench Pro V2 采用官方 locked protocol：Agent 阶段离线，仅放行模型端点；捕获补丁后在干净容器中重新评分；每任务 50 分钟。自己的 Agent 适配器应复现同等约束，修改协议则单列报告。[官方 V2 说明](https://github.com/scaleapi/SWE-bench_Pro-os/blob/main/v2/README.md)

Terminal-Bench 4.0 调整资源、修复任务并移除部分任务，官方 Agent 超时预算为 8 小时。若我们使用较短研究预算，要明确标注，不能与官方榜单数字直接比较。固定任务版本、容器镜像与资源配置，不在实验中自动跟随 latest。[4.0 官方公告](https://www.tbench.ai/news/terminal-bench-4-0)

2.1 修复了 2.0 中的任务问题。2.0、2.1、4.0 的分数应分开报告；不同版本不视为彼此独立的迁移测试，需检查任务关系。[2.1 官方公告](https://www.tbench.ai/news/terminal-bench-2-1)

Verified 仍可作为历史参考。OpenAI 的审计指出测试设计与训练污染风险，因此不应让它独自支撑“真实泛化”的结论；其审计的错误比例来自特定失败子集，不能套用到整个数据集。[审计原文](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)

跨语言评测不是首轮硬性要求。若主张一般软件工程策略，再使用 42 个仓库、9 种语言的 Multilingual，审计与所有训练来源的仓库交叉。[官方说明](https://www.swebench.com/multilingual)

## 训练与开发数据

- 代码训练：优先 SWE-smith 的可执行任务及其生成流程，SWE-Gym 作为真实任务补充；按实际仓库来源拆分，排除最终测试仓库和任务变体。[SWE-smith 官方仓库](https://github.com/SWE-bench/SWE-smith)
- 终端训练：优先核验 Tmax 的文本终端任务和程序化 verifier，先取小规模可复现子集，不直接混入整个多模态任务池。[Tmax 作者仓库](https://github.com/hamishivi/tmax)
- 扩展候选：TaskTrove 的代码/终端子集。它同时包含有 verifier 与无 verifier 的任务；RL 和效用反馈优先选可执行验证子集，单独审计来源。[TaskTrove 说明](https://github.com/open-thoughts/OpenThoughts-Agent/blob/main/data/tasktrove/tasktrove_v2_README.md)
- 开发/Meta-validation：从上述训练候选中独立划分；代码按仓库，终端按任务来源、生成模板、环境和技能组合分组。随机拆分实例不能保证独立。
- 最终测试：仅评测。任务答案、隐藏测试、最终成绩和轨迹不反馈给 Trainer，不用于筛选经验或选择检查点。

既有 SEAL 和 AZR 代码继续作为机制参考。新增代码与终端执行层建议围绕 Harbor 建立统一日志、容器和 Agent 接口；遵守各 benchmark 的独立评分协议。[Harbor 官方文档](https://docs.harborframework.com/)

## 首轮执行顺序

1. 建立任务清单，记录来源、仓库、模板、镜像、verifier 与 split。对训练和测试进行身份及近重复检查。
2. 每个领域先在独立开发集选约 20–30 个覆盖不同难度的任务，检查环境、参考解和失败模式。该数量是试跑建议，不是正式评测规模。
3. 固定一个初始模型、Agent 工具、提示和预算，确认它能获得可学习反馈。若接近零成功率，先做统一热身或调整模型；正式测试前冻结选择。
4. 同一经验池比较：无记忆、外部记忆、直接轨迹 SFT、较强经验蒸馏、蒸馏加记忆。RL 若加入则单独记账，计入新 rollout。
5. 机制确认有用后，追加学习选择策略及 fresh Solver 重置实验。
6. 冻结方法和检查点，再运行两个主测试。参考测试用于对齐；预算有限时减少候选方法，主结果保留完整任务集及重复运行。

## 需要报告的结果

分别报告代码与终端的任务成功率，不混成单个总分。至少比较三个随机种子或独立运行，给出任务配对差值和置信区间；以任务为重采样单位，重复轨迹不当作独立任务。

持续性报告按顺序到来的新任务表现，以及第 1、3、5 轮后的独立旧任务保留表现。封存测试只用于分析，不决定是否更新、回滚或停止；这些决定来自开发集。

成本包含经验获取、验证、教师生成、训练、策略搜索与部署推理，并区分 GPU 时间、CPU/容器资源、模型调用和 token。高成本终端任务尤其需要固定资源，区分模型失败与基础设施故障。

跨域迁移分别测试代码经验 → 终端任务、终端经验 → 代码任务；混合训练在两套测试上变好本身不证明迁移。

如果所有组在困难测试上都接近零，或增益仅来自看到当前题的历史答案，不能将其解释为可靠持续改进；应通过独立开发集调整后续研究设计，并披露已经使用过的测试结果。
